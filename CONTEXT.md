## 1. What we're building

**Antigravity** is an AI-powered, multi-tenant, **configuration-driven** Enterprise Workspace Platform. Organizations pick an industry blueprint (IT, Healthcare, Education, Finance, Manufacturing), customize it, and receive an **isolated workspace** whose navigation, dashboards, pages, widgets, roles, and permissions are **generated from backend configuration** — not hardcoded in the frontend.

The core idea: **the frontend is a pure rendering engine over a server-produced "Workspace Manifest."** The backend compiles that manifest per user from four independent config layers. Nothing about what a user can see or do is decided in the browser.

**Not** a fixed dashboard app. It is a *workspace generation platform*.

## 4. Architecture in one screen

**Three engines on a tenant-isolated data layer:**

1. **Identity & Tenancy** — Supabase Auth JWT carries `tenant_id`/`user_id`; RLS enforces isolation at the DB; NestJS enforces RBAC above it. Defense in depth.
2. **Configuration Engine (the heart)** — compiles a per-user **Workspace Manifest** from four layers:
   `Blueprint (L1) → Tenant Config overrides (L2) → Entitlements (L3) → Identity/Permissions (L4)` → validated, versioned JSON, already permission-pruned.
3. **SDUI Rendering Engine** — Next.js interprets the manifest against a **closed, versioned primitive registry** (`Stack`, `Grid`, `Table`, `Form`, `Chart`, `KpiCard`, composites, …); Zod-validated per node, per-node error boundaries, graceful unknown-node fallback.

**Non-negotiable invariants:**
- Permissions resolved **server-side**; unauthorized elements are absent from manifest bytes (**prune, not hide**).
- Data bindings & actions are **named, server-authorized references** — never raw queries/mutations in the manifest.
- Every data source enforces **tenant + data-scope** independently of RLS.
- Tenant-safe RAG retrieval (tenant-tagged embeddings + RLS + explicit filter + post-retrieval permission re-check).

## 6. Glossary (shared vocabulary)

- **Workspace Manifest** — the per-user JSON document the server compiles; the frontend renders it verbatim.
- **Blueprint (L1)** — platform-owned default config for an industry.
- **Tenant Config (L2)** — an org's structured overrides on its blueprint.
- **Entitlements (L3)** — which modules/features a plan unlocks.
- **Permission Resolver** — server service turning a user's roles into an effective `resource:action:scope` permission set.
- **Primitive** — a registered, versioned UI building block the renderer understands.
- **Composite widget** — a module-provided rich component registered into the primitive registry (escape hatch).
- **Data source** — a named, server-authorized read query referenced by manifest bindings.
- **Mutation** — a named, server-authorized write referenced by manifest actions.
- **Prune-not-hide** — unauthorized UI is removed server-side, never sent to the client.

## 9. Prisma 7 connection model (load-bearing — read before touching the DB layer)

Discovered during Stage 1; materially different from what the original plan assumed, so it's captured here rather than left buried in the changelog:

- **No `datasourceUrl` client option and no `directUrl` schema field.** Both were removed in Prisma 7. `apps/api/prisma.config.ts` supplies exactly one `datasource.url` — used only by the CLI (`migrate`, `studio`, `db execute`) — currently set to `DIRECT_URL` (the elevated Supabase `postgres` role).
- **The running app never reads `prisma.config.ts`'s URL.** It must construct its own `PrismaClient` with an explicit driver adapter: `new PrismaClient({ adapter: new PrismaPg({ connectionString: process.env.DATABASE_URL }) })`, using `@prisma/adapter-pg` (already installed). `DATABASE_URL` points at the restricted `app_runtime` role (`NOBYPASSRLS`) via Supabase's pooled connection.
- **Supavisor (Supabase's pooler) requires the project ref suffixed onto the username** for every role, not just the default `postgres` role — e.g. `app_runtime.ncvsrhloagkvfidasels`, not bare `app_runtime`. Omitting it fails with `ENOIDENTIFIER`.
- **RLS policies use `NULLIF(current_setting('app.tenant_id', true), '')::uuid`**, not a bare cast — on a pooled connection, an unset GUC can read back as `''` rather than `NULL` once it's been set at least once on that physical connection, and `''::uuid` throws instead of failing closed.
- The multi-file schema folder (`prisma/schema/*.prisma`) works with zero preview flags in v7 — folder-based schemas are stable now.
- Generated client lives at `apps/api/src/generated/prisma` (gitignored, regenerated via `postinstall: prisma generate`) and is **TypeScript source**, not a prebuilt package — it compiles as part of the app's own build. It's under `src/` deliberately: TypeScript's `rootDir` inference would otherwise shift once anything imports it, breaking `dist/main.js`'s expected output path.
- **⚠️ Never `Promise.all` multiple queries against the same `tx` parameter inside a mutation/data-source `resolve()`.** Every resolver's `tx` comes from `TenantPrismaService.run()`'s `$transaction(async tx => ...)` — an interactive transaction bound to **one reserved connection**. Prisma explicitly documents concurrent queries against one interactive-transaction client as unsafe; it corrupts the connection's state, surfacing unpredictably (sometimes well after the offending line) rather than failing immediately at the call site. This caused a real, user-reported production bug (`user.invite` 500ing with an opaque `ERR_HTTP_HEADERS_SENT` — see the RBAC precision upgrade's bug-fix entry, §31) and was found lurking in two more places once swept for. **Sequential `await`s only, whenever two or more queries share one resolver's `tx`.** Queries against *different* `tx`s (e.g. two separate `tenantPrisma.run()` calls, as `compiler.service.ts` does) are unaffected — the danger is specifically sharing one transaction's one connection, not `Promise.all` in general.

## 13. Shared manifest-schema package (Stage 5 — reuse this, don't rebuild it)

Everything under `packages/manifest-schema/src/` — the single source of truth for the manifest contract, imported by both `apps/api` and `apps/web` as `@antigravity/manifest-schema`:

- **Built as CommonJS, deliberately — do not add `"type": "module"` back.** It was ESM initially; that broke the *actual compiled API server* at boot (`ERR_MODULE_NOT_FOUND`, not just a test failure) because Node's ESM resolver requires explicit `.js` extensions on relative specifiers that `tsc` doesn't emit by default, on top of Jest's CommonJS `require()` being unable to parse `export *` syntax at all. `apps/api` compiles to CommonJS (NestJS's standard mode) and Next.js consumes either format transparently, so CJS-only is the correct choice for this package, not a workaround to revisit. If a real need for ESM output ever arises, that means a proper dual-build (e.g. `tsup`), not flipping `"type": "module"` back.
- **`UINodeSchema` and `NavItemSchema` are recursive** (`children` self-reference) via `z.lazy()` with an explicit `z.ZodType<T>` return-type annotation — TS can't infer a recursive type through `z.lazy()` without it.
- **`keyedListPatchSchema<T>(itemSchema)`** in `keyed-list-patch.ts` is the one generic factory for the stable-id add/remove/patch mechanism — reuse it for any new keyed-list override rather than hand-rolling another. Note: `patch` values are validated loosely (`Record<string, unknown>`), not via `itemSchema.partial()` — Zod's `.partial()` doesn't compose with `ZodLazy` in v4, so strict partial-shape validation was deliberately dropped in favor of it working at all. `add.item` is still fully validated.
- **`ConfigEngineService.compileWorkspace`** calls `WorkspaceManifestSchema.parse()` on its own output before returning, and **`prisma/seed.ts`** validates blueprint fixtures against `BlueprintDefinitionSchema` before upserting — both are real runtime guarantees now, not just compile-time types. Follow this pattern for new blueprint/manifest-producing code.
- **When changing anything here, verify both consumers for real** — a clean `tsc`/`next build` is not sufficient proof apps/web can actually resolve the package (nothing may reference it yet). Confirm with a real import that renders/executes, the way `apps/web`'s homepage currently proves it (`MANIFEST_SCHEMA_VERSION`) — and confirm apps/api specifically by *running the compiled `dist/main.js`*, not just `nest build` succeeding, since module-resolution failures only surface at actual runtime, not at typecheck time.

## 14. Workspace delivery API (Stage 6 — reuse this, don't rebuild it)

Everything under `apps/api/src/workspace/`, `data-sources/`, and `mutations/`:

- **`ConfigEngineService` is now two halves, and that split matters.** `resolveIdentity(tenantId, user)` is cheap (tenant + active tenant-config row + resolved permissions — no blueprint JSON, no pruning) and is *all* `getEtag()` needs. `resolvePrunedBlueprint(identity)` is the expensive half. **Always check the etag before doing expensive work** — that's the entire point of the split, and any new endpoint that needs to compile something should follow the same pattern: cheap identity/etag check first, expensive resolution only on a cache miss.
- **`compilePage` returns `null` for both "page doesn't exist" and "page was pruned for this user"** — the controller 404s identically either way. Don't special-case these differently in a future change; distinguishing them would leak information about pages a user isn't allowed to know exist (the same prune-not-hide principle as the manifest itself, ARCHITECTURE §6.4).
- **ETags are quoted on the wire** (`ETag: "abc123"`, per HTTP spec) — `etagMatches()` in `config-engine/etag.ts` handles both quoted and bare comparison plus comma-separated candidate lists, but always *emit* the quoted form. Reuse `etagMatches`, don't hand-roll another comparison.
- **`/api/data/:source` and `/api/mutations/:mutation` are stubs that 404 for every name** — this is intentional and *shouldn't change in shape* when Stage 8 adds real registries, only in which names resolve. If a name-not-found case ever needs to look different from "not implemented yet," that's a Stage 8 concern, not a reason to touch these stub controllers now.
- **`CurrentUserService`** (`tenancy/current-user.service.ts`) resolves the internal `User` row from the request's auth context — every new guarded controller that needs "who is making this request" should inject this, not re-fetch the user inline (that pattern was duplicated twice before being extracted here).
- **`GET /me/workspace` no longer exists** — it was Stage 4's temporary verification route, explicitly superseded by `GET /api/workspace/bootstrap`. `GET /me` and `GET /me/permissions` are unrelated and still present.
- **⚠️ The etag MUST reflect blueprint content, not just `Blueprint.version`, or browsers silently serve stale pages via `304` — this caused a real, user-reported bug (post-Stage-9).** `Tenant.blueprintVersion` is a version *number* that Phase 1's normal workflow (editing `prisma/seed.ts` and re-running it) does **not** bump on a content fix — it upserts the same `(industry, version)` row in place. Since `Cache-Control: private, no-cache` makes browsers auto-revalidate via `If-None-Match`, an unchanged etag across a real content change means the browser's stale cached copy gets confirmed as "still valid" forever, even though the actual manifest changed. **Fixed:** `resolveIdentity()` now also selects `Blueprint.updatedAt` (a new column, `@updatedAt`-managed, added specifically for this) and folds it into the etag hash. **If you ever add another mutable-content root table that participates in the manifest (new blueprint-like data, a second `TenantConfig`-style layer, etc.), give it the same treatment — a version *number* alone is not sufficient proof of content freshness unless something guarantees it's bumped on every edit, and the seed-script upsert pattern does not guarantee that.**

## 15. Frontend / SDUI renderer (Stage 7 — reuse this, don't rebuild it)

## 16. Projects module & the data-source/mutation registry pattern (Stage 8 — reuse this, don't rebuild it)

**Read this before starting Stage 9 (Tasks) — it's built to be copied, not reinvented.**

- **`DataSourceRegistry`/`MutationRegistry`** (`apps/api/src/data-sources/`, `mutations/`, both `@Global()`) are the one place new named sources/mutations get registered. A feature module's registrar (see `ProjectsRegistrar` in `modules/projects/projects.module.ts`) implements `OnModuleInit` and calls `.register()` for each definition it owns. `DataSourcesController`/`MutationsController` dispatch by name and 404 anything unregistered — that behavior doesn't change as more modules add real names.
- **Two-layer authorization, and both layers matter:** the controller checks *presence* of `requiredPermission` (does the user have this grant at any scope) before even calling the resolver; the resolver itself is responsible for *scope* — either baking it into the query's `where` clause (list/count-style reads, see `projectsWhere` in `projects.data-sources.ts`) or checking `isRowInScope()` (`rbac/scope-check.ts`) after fetching a specific row (update/delete-style mutations, see `projects.mutations.ts`). New data sources/mutations must implement both layers — the controller-level check alone is not enough.
- **`isRowInScope()` needs `{ ownerId, departmentId }` on the row and `{ userId, departmentId }` on the actor.** If a future row type doesn't have a `departmentId` column, `"department"`/`"team"` scope for it needs its own decision — don't assume the Project pattern transfers automatically.
- **Real bug, now guarded by a regression test — read before writing a scope filter against a UUID column:** never use a sentinel string (e.g. `"__no_department__"`) as a fallback value in a `where` clause against a Postgres `uuid` column. It doesn't mean "match nothing" — the query fails outright (`invalid input syntax for type uuid`), a 500, not an empty result. When a scope filter has no valid value to filter by, skip the query and return empty results in application code (see `projectsWhere`'s `null` return, and `projects.data-sources.spec.ts` for the exact regression test).
- **Composites gate their own controls via action presence, not a separate permission check.** `ProjectBoard`'s "+ New Project" control only renders if `actions` (already pruned server-side) contains a `project.create` mutation — it does *not* re-check permissions client-side. Follow this pattern for any new composite control: presence in the (already-pruned) manifest *is* the authorization check on the frontend; the backend enforces it for real regardless.
- **Dynamic user input bypasses `ActionSpec.input` resolution, deliberately.** `ActionSpec.input` (a static `BindExpr`) works for `{ ref: "row.id" }`-style cases where the value comes from render context, but not for "whatever the user just typed in a text box." `ProjectBoard` calls `callMutation()` directly for its create flow instead of going through `useActionDispatch`. This is the intended pattern, not a workaround — expect Stage 9's Task creation (if any) and any future form-driven mutation to do the same.
- **No page-level filter/query state exists yet.** `FilterBar`/`SearchBar` remain visually present but non-functional (Stage 7 note, still true). Don't assume `projects.list`'s `status` param is reachable from the UI yet — it's only exercised via the dashboard's hardcoded `{ const: "active" }` binding today.
- **Phase 1 has no per-record detail-view routing.** The dead `page.project-detail` navigate action was removed, not replaced — there is no mechanism yet for a page parameterized by a specific record's id (`GET /api/workspace/pages/:pageId` serves *static* pages only). If a future stage needs a detail view, that's a real gap to design, not something to patch around.
- **⚠️ `Project` now has a real many-to-many members concept (`ProjectMember`, see §27) — don't confuse it with `ownerId`/`departmentId`.** `ownerId` is "who created it" (single), `departmentId` is a coarse team-scope match, and `members` (via `ProjectMember`) is "who was explicitly assigned to work on it" (many) — three independent, all-still-active ways a row can be in a viewer's scope. `projectsWhere`'s team/department branch now ORs all three non-tenant/non-own paths together (assigned task, project membership, department match) — read §27 before touching that function again.

## 17. Tasks module (Stage 9 — reuse this, don't rebuild it)

**§16 (Stage 8) is a prerequisite read — this section only covers what's different for Tasks.**

- **`Task` has no `ownerId`/`departmentId` columns** (unlike `Project`). The adaptation, not a deviation from the pattern: "own" scope maps to `assigneeId`; "department"/"team" scope reaches the department by joining through the owning `Project` — `where: { project: { departmentId } }` for reads (`tasksWhere` in `tasks.data-sources.ts`), and `include: { project: { select: { departmentId } } }` before calling `isRowInScope()` for the row-level check in `task.updateStatus`. `isRowInScope()` itself needed zero changes — callers adapt their own row's fields to its generic `{ ownerId, departmentId }` shape, exactly as anticipated in §16.
- **Security property worth re-checking if this file is ever touched:** a client-supplied `assigneeId` filter param must be *overridden* by "own" scope, not merged with it — applied in `tasksWhere` by writing the scope-mandated fields *after* the client-supplied ones (field-assignment order is the enforcement mechanism; don't reorder those two blocks). Covered by an explicit test in `tasks.data-sources.spec.ts`.
- **Formerly a known gap here, now fixed twice over — see §21 and §26.** This section originally documented (2026-07-15) that a Member with no department set saw **zero** team-scoped rows, including their own creations, since `isRowInScope()` required an exact `departmentId` match and nothing ever populated one. The HR module (§21) made department assignment real, closing the gap for the department-matches case. §26 then fixed the deeper structural issue underneath it: ownership/assignment is now always an inclusive **floor** under team/department scope (OR, not AND) — so "assigned to me" is sufficient on its own regardless of department, matching or not. A Member with no department at all now still sees rows assigned to them.
- **When testing cross-user authorization, use a genuinely separate `User` row (and separate Supabase auth account) — never just reassign one user's role.** Swapping a single user's role from Admin to Member and expecting `own`-scope restrictions to kick in on their own prior work will not exercise the check correctly (they still own what they created, regardless of current role) and can look like a false-positive security bug. This exact mistake happened during Stage 9's live verification, was caught, and re-verified correctly with a second real user — see CHANGELOG Session 2 for the full account.
- **`TaskList`'s create flow fetches `projects.list` itself**, directly via `callDataSource` (not through `bind`) — a project picker is this composite's own UI need, not data the node's `bind` describes. Same reasoning as why `ProjectBoard`'s create flow bypasses `ActionSpec.input` resolution (§16) — ad hoc composite-level data fetching for a composite's own UI, not a new general pattern to formalize yet.
- **Status is a fixed 3-value UI vocabulary (`todo`/`in_progress`/`done`), not a DB-enforced enum** — `Task.status` is still free-text (`tasks.prisma`). Don't assume the DB rejects other values; nothing currently stops a direct API call from setting an arbitrary status string.

## 18. Notifications module (Stage 10 — reuse this, don't rebuild it)

`apps/api/src/modules/notifications/` and `apps/web/src/modules/notifications/NotificationBell.tsx`:

- **Notifications have no permission gate — ownership *is* the authorization.** Unlike every other data source/mutation in this codebase, none of `notifications.list`/`notifications.unreadCount`/`notification.markRead`/`notification.markAllRead` set `requiredPermission`, and none call `isRowInScope()`. Revisit only if/when Projects grow an actual membership list.
- **The "who gets notified" decision is a pure, exported, unit-tested function** — `notificationRecipientFor(assigneeId, actorId)` in `tasks.mutations.ts` (`null` for both "no assignee" and "actor is the assignee"; the assignee id otherwise). If a third notification-emitting event is ever added, reuse this function rather than re-deriving the same "don't notify yourself" check inline.

Phase 1's page model has no mechanism for a node to live outside one specific page's tree (no shared "header region" concept), so anything that must appear on *every* page has to be chrome, not a page node. If a future stage needs more chrome-level widgets like this, this is the established precedent — don't invent a blueprint-level "global slots" concept until something actually needs more than one.

## 19. Stage 11 / Phase 1 completion — process findings (read before any future DB reset)

`prisma migrate reset` was run once, against the live Supabase project, with the user's explicit consent (there is no separate local/dev database in this setup — the live Supabase project *is* the only one). Two things worth knowing before doing this again, ever:

- **Prisma 7 has a built-in AI-agent safety gate on `migrate reset`.** If it detects it was invoked by an AI coding agent, it refuses to run and instead prints a mandatory disclosure (exact command, motivation, irreversibility, a dev-vs-prod prompt) that the agent must relay to the user verbatim, then requires a **fresh, explicit** confirmation — it explicitly does not accept prior conversation turns as consent, even an unambiguous prior "yes." The rerun needs `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION=<the user's exact new consent text>` set as an environment variable. This is Prisma's standing behavior, not a one-off — expect to go through this flow again for any future reset.
- **`prisma migrate reset --force` did NOT auto-run the seed script**, despite `seed: "tsx prisma/seed.ts"` being correctly configured in `prisma.config.ts` (which is supposed to make resets auto-seed). Confirmed by querying `blueprints` directly after the reset — 0 rows, despite all 4 migrations having applied cleanly. Not root-caused (not worth the time for a one-off dev-database operation with no automated pipeline depending on it) — **the workaround is to always run `pnpm run prisma:seed` manually right after any reset, and verify the blueprint table isn't empty before doing anything else.** Don't assume a reset leaves a working, seeded database.
- **Any future DB reset will delete every real tenant/user in the system**, including whatever the user is currently using to test in the browser — always check `prisma.tenant.findMany()` first and confirm with the user before running one, the same way this one was handled. There's no staging/prod split to fall back on for a "safe" reset target.

## 22. Stage 12: Prototype Polish — design system, theming, and dynamic filters (reuse this, don't rebuild it)

`apps/web/src/ui/`, `apps/web/src/app/globals.css`, `apps/web/src/sdui/filter-state.tsx`, and every primitive/composite (restyled in place):

- **Before this stage, `apps/web` had zero CSS infrastructure of any kind** — no `globals.css`, no Tailwind/CSS Modules/styled-components, every component used inline `style={{}}` objects. This wasn't a partial migration; it was a from-scratch build. Confirmed by direct exploration before starting, not assumed.
- **Token architecture — read this before changing any color.** Actual color *values* live as plain CSS custom properties on `:root` (light) and `.dark` (dark, the default theme) in `globals.css` — e.g. `--accent: #4f46e5`. Tailwind v4's `@theme` block maps these into real utility classes (`@theme { --color-accent: var(--accent) }` → `bg-accent`, `text-accent`, etc. all work as normal Tailwind classes). This two-layer indirection is what makes both dark/light toggling (`next-themes` swaps which block's variables are active) **and** per-tenant branding overrides (`Tenant.branding.accentColor`, applied as an inline `style={{ "--accent": ... }}` on the workspace shell's root div) work simultaneously — don't collapse this into a single-layer Tailwind config, the indirection is load-bearing, not incidental complexity.
- **The `ui/` kit (`Button`, `Input`, `Select`, `Card`, `Badge`, `Skeleton`, `Alert`, `Toast`, `Dropdown`, `CommandPalette`, `icons.ts`) is the one place new visual patterns should be added.** Every primitive and composite imports from here rather than hand-rolling Tailwind classes inline for anything that recurs (buttons, form fields, cards, loading states). If a new SDUI primitive needs a control that doesn't exist yet in `ui/`, add it there first, then consume it — don't duplicate ad hoc styling in the primitive itself, the exact problem this stage fixed.
- **`Alert` (inline, tied to a specific form/action) and `Toast` (global, `useToast()`, auto-dismissing) are deliberately two different mechanisms, not one.** Validation/mutation errors that need to stay visible next to the control that caused them use `Alert`; success feedback for a completed action (create/invite/assign) fires a `Toast`. Don't collapse these — an error that auto-dismisses after 3.5s is a bad pattern, and a permanent inline "Project created" banner would clutter the UI needlessly.
- **The one real architecture addition this stage, not just a visual one: page-scoped dynamic filter state (`filter-state.tsx`).** `FilterBar` used to render disabled, non-functional placeholders. Now: a blueprint's `FilterBar` node declares its available filters and their option lists via `props.filters: [{ key, label, type: "select", options }]` — still entirely config-driven, nothing hardcoded in the component. `FilterStateProvider` (mounted once per rendered page, keyed by page id so it resets on navigation — see `workspace/page.tsx`/`[pageId]/page.tsx`) holds the live filter values; `use-data-binding.ts`'s ref-resolution context grew a **third namespace** — `{ user, tenant, filters }` — so any sibling node's `bind.params` can reference `{ ref: "filters.status" }` and get real, live re-fetching when the filter changes (the effect's dependency array includes a stringified snapshot of `filters`). If a future page needs its own filters, follow this exact pattern: add a `filters` config to that page's `FilterBar` node in the blueprint, and reference `{ ref: "filters.<key>" }` in the bound node's `params` — no new frontend plumbing required, the mechanism is already generic.
- **`Chart` (`recharts`) is deliberately one donut chart, not a general charting primitive with type/variant options.** It was added because a dashboard chart was explicitly requested, backed by a new data source (`projects.statusBreakdown`, same `projectsWhere` scope-filtering as every other Projects data source, grouped via Prisma's `groupBy`). Extend it (a `type` prop for bar/line) only when a real page needs a second chart shape — don't speculatively generalize now.
- **Chart colors are CSS `var()` strings** (`"var(--color-accent)"`, etc.) passed directly as `recharts`' `fill` prop, not fixed hex values — this makes the chart automatically theme-reactive (light/dark) for free, since SVG `fill` accepts custom properties in evergreen browsers. If a future chart needs colors, reuse this pattern rather than hardcoding a separate palette.
- **`SearchBar` remains intentionally inert** — restyled to match the new design system but still not wired to anything, same documented-placeholder status as before this stage. Only `FilterBar` got the real mechanism, because only `FilterBar` was explicitly requested to be made functional.
- **⚠️ `page.projects` no longer uses `FilterBar` (see §27) — the mechanism above is still real, live infrastructure, just currently unused anywhere in the seeded blueprint.** `page.projects` was rebuilt around `ProjectBoard` to carry real Project↔Member assignment, replacing the `FilterBar`+`Table` combo this stage built. `filter-state.tsx`, the `use-data-binding.ts` `filters` ref-namespace, and `FilterBar` itself are all untouched and fully functional — the next page that needs a real filter should reuse this exact pattern, not rebuild it. Don't read "zero current usages" as "the feature was removed."
- **A real, disclosed tooling limitation, not a corner cut: I have no way to take a screenshot or drive a browser.** Every other stage this session that touched the frontend was followed by the user's own hands-on browser testing, which is what actually validated the visual/interactive result. For this stage specifically, my own verification was necessarily narrower: `pnpm -r run typecheck`/`test` staying green (66 backend + 1 frontend, unchanged — proving the restyle didn't alter any behavior the existing tests assert), inspecting server-rendered HTML directly to confirm Tailwind classes/fonts/theme script are actually present and correctly formed, and a full scripted pass against the live Supabase project confirming zero regressions across every existing feature plus the two new mechanisms (dynamic FilterBar, `statusBreakdown`). **None of that is the same as confirming the UI actually looks good** — that determination is still entirely the user's, and as of this writing they had not yet reviewed it live.

## 23. Settings & Workspace Customization (Phase 2, Stage 2 — reuse this, don't rebuild it)

`apps/api/src/modules/settings/`, `apps/web/src/modules/settings/WorkspaceSettings.tsx`, `apps/web/src/sdui/render-context.tsx`'s `refetchBootstrap`:

Any future mutation that needs to touch a root-table (`Tenant`, `Blueprint`, `Plan`) rather than a tenant-scoped one should follow this same shape.
- **`RenderContextValue.refetchBootstrap()` is a new, generically useful capability, not a Settings-specific hack.** Before this stage, every composite only ever needed to refresh its own bound data (`useDataBinding().refetch()`) — nothing previously touched data that lives in the workspace *shell* itself (`manifest.navigation`, `manifest.tenant`) rather than one page's content. - **Verified live, entirely through a throwaway tenant** (never the real Admin's password) — branding round-trip + etag freshness, the `TenantConfig` versioning invariant (checked directly against the DB, not just through the API), and the merge-doesn't-clobber property (renamed two different nav items, confirmed both overrides survived in the final compiled manifest simultaneously). See CHANGELOG for the full run.

- **Fixed structurally, not per-incident**: `apps/api/prisma/seed.ts`'s `main()` now re-syncs every existing tenant's blueprint-sourced `Role` rows (matched via `sourceBlueprintRoleId`, scoped by industry) to the blueprint's current permission list, on every seed run — full overwrite, not a merge, which is safe only because Phase 1 has no per-tenant role-customization mechanism (unlike nav/branding). **Any future stage that adds a new permission to a blueprint role must re-run the seed script** (already standard practice — reseeding is already done after every blueprint content change, for the etag to pick it up) — the re-sync now happens automatically as part of that same step, nothing extra to remember there. What *is* new to remember: **live verification for any future permission-gated feature must also directly check the real tenant's stored `Role.permissions`** (a DB query, not a login) to confirm the real Admin actually received the grant — testing only a throwaway tenant's Admin will structurally always look correct and miss this class of bug.

- **Verified live** via a scripted throwaway Admin+Member pair: a messy workspace ID round-tripped to a clean slug with no error; a project created with no department, containing a task assigned to a Member with no department, was correctly visible to that Member via `projects.list`/`tasks.list` — the exact previously-broken scenario. 7 new/updated unit tests across `scope-check.spec.ts`/`tasks.data-sources.spec.ts`/`projects.data-sources.spec.ts`. ## 29. Role hierarchy — extends-chain inheritance (reuse this, don't rebuild it)

`apps/api/src/rbac/grant-resolution.ts` (`resolveBlueprintRoles`), `apps/api/src/auth/materialize-roles.ts` (`materializeBlueprintRoles`), `packages/manifest-schema/src/blueprint.ts` (`extends` field), `apps/api/prisma/seed.ts` (the 8-role fixture):

- **The flat 2-role (Admin/Member) model is gone — replaced by an 8-tier `extends`-chain hierarchy.** `role.intern` (base, no `extends`) → `role.member` (relabeled **"Employee"**, `extends: "role.intern"`) → `role.senior-employee` → `role.team-lead` → `role.project-manager` → `role.department-head`, plus `role.hr-manager` as a **separate branch** extending `role.member`/Employee (not nested under Department Head), and `role.admin` (relabeled **"Company Admin"**, still flat/unchanged, still has more than the union of everything below it). **The user's original diagram was an org chart (reporting lines), not a literal permission graph** — confirmed via `AskUserQuestion` before designing anything, since the diagram showed lines converging from two different roles (HR Manager and Team Lead) into the same children, which isn't expressible through a single-parent `extends` (matches `extendsRoleId`'s single-FK shape). If a future request describes another org-chart-shaped diagram, don't assume it's a literal RBAC structure — ask.
- **`resolveBlueprintRoles` is the one new piece of core logic, and it's mostly wiring.** `applyGrantDeltas` (`+`/`-` prefixed delta application) already existed, fully unit-tested, since long before this stage — its own doc comment already said it would run "at role materialization time," it just never had a caller. `resolveBlueprintRoles` walks a blueprint's `extends` chains (memoized recursion, cycle/unknown-target detection) and calls `applyGrantDeltas` at each step. **Pure, DB-free, unit-tested** — same category as `applyGrantDeltas`/`collapsePermissions`/`isRowInScope`.
- **⚠️ `resolveEffectivePermissions`/`collapsePermissions`/`isRowInScope` are completely unchanged.** Extends-chain resolution is a blueprint/*materialization*-time concern only — by the time a `Role` row exists in the DB, `permissions` is already the fully flattened list, exactly like every role before this stage. If a user is assigned multiple roles at once (a separate, already-working mechanism via multiple `RoleAssignment`s), that union still happens exactly as before — unrelated to any single role's own `extends` chain. Don't go looking for extends-chain logic anywhere near request-time permission checks; it isn't there and shouldn't be.
- **`materializeBlueprintRoles` is now the single, shared path for creating/refreshing a tenant's `Role` rows** — used by both `AuthService.signup` (brand-new tenant, every role created) and `seed.ts`'s reseed step (existing tenants — missing roles created, existing ones refreshed). **This replaced a real gap the old re-sync mechanism had**: the previous `updateMany`-only re-sync could only ever patch permissions on roles a tenant *already had* — it had no way to create a role a tenant had never seen before. That was fine when every blueprint change only ever added a permission to an existing role (HR's `department:manage`, Settings' `settings:manage`), but this stage added 6 brand-new roles, and the old mechanism would have silently done nothing for them on every existing tenant. **If a future blueprint change adds a new role, this is already handled correctly** — no special-casing needed, just add the role definition and reseed.
- **Relabeling `role.admin`/`role.member`'s existing rows was a deliberate zero-migration choice.** Their blueprint `id`s (`sourceBlueprintRoleId`) are unchanged — only `label` changed (and `role.member`'s internal shape, restructured from a flat list into `extends`+deltas whose flattened union is identical to the old flat list). Every existing `RoleAssignment` — including the real standing Member test account's — keeps pointing at the exact same `Role` row, verified live (same `roleId` before and after reseed).
- **⚠️ `department:manage:tenant` has no department-*scoped* variant — a real, flagged gap, not an oversight.** The HR module never built one; it's a single flat tenant-wide triple. So "Department Head" in this hierarchy does **not** get department-management rights, even over their own department — only HR Manager and Company Admin do. Giving it to Department Head would let them edit *every* department tenant-wide (broader than the title implies). If department-scoped `department:manage` is ever wanted, that's a real, separate follow-up (a new scope dimension on an existing permission), not a quick reassignment in the blueprint fixture.
- **No frontend changes were needed, and this is worth remembering as a design confirmation, not luck**: `TeamMembers.tsx`'s invite-role dropdown was already built generically off `roles.list` with zero hardcoded assumptions about role count — the 8 roles simply appeared as more options. Any future module's own role-aware UI should follow this same "read from the registry, never hardcode role names/count" discipline.
- **Live-verified against every real tenant, not just a throwaway signup** (this stage touches existing data, unlike most prior stages): captured a before/after snapshot, reseeded, and confirmed both real "Magar Limited" tenants (`magar-limited`, `yash-1`) ended up with exactly 8 roles each, `role.admin`'s permissions byte-identical to before, `role.member`'s flattened permissions equal as a *set* to its old flat list, and the standing Member account's `RoleAssignment` unmoved. A fresh throwaway signup + inviting a "Team Lead" and calling `GET /me/permissions` confirmed the flattened, *collapsed* permission set matched the designed chain exactly, including negative checks (no `user:manage` leaking in from the HR Manager branch, no `project:delete:department` leaking in from Department Head).
- **Also found and cleaned up during this stage's verification, unrelated to the feature itself**: 5 leftover throwaway tenants from earlier in this session that were never cleaned up after an earlier verification round, and a stale fact in this very file (the user's real Workspace ID was recorded as `magar-limited-2`; the live DB shows it's actually `yash-1`, almost certainly changed by the user themselves via the Workspace ID edit feature after §25 fixed it). Both corrected. **A reminder to periodically sanity-check facts recorded here against the live DB, not just trust the last time they were written down** — this project moves fast enough, and the user tests hands-on often enough, that recorded facts can go stale within the same session.

## 31. RBAC precision upgrade — distinct responsibilities per tier (reuse this, don't rebuild it)

`apps/api/src/rbac/role-hierarchy.ts` (`isRoleAssignable`/`isRoleAssignableBy`), `users.mutations.ts` (`user.changeRole`, `user.invite`'s hierarchy check, `user.assignDepartment`'s scope check), `hr.mutations.ts` (`department.create`/`team.create` scope checks), `tasks.mutations.ts` (`task.reassign`, the project-membership check on `assigneeId`):

- **`user:invite` and `user:manage` are now genuinely separate permissions.** Before this stage they were one grab-bag (`user:manage`) gating both invite and org-placement. Only Company Admin has `user:invite:tenant`; HR Manager does not — reserved for the still-unbuilt delegation stage (§ "Next up" in CHANGELOG). **If you're about to gate a new user-affecting mutation, ask which bucket it's really in** — creating a brand-new person is `user:invite`, changing an existing person's org placement/roster visibility is `user:manage`, changing their role is the separate `role:assign` below. Don't default back to one grab-bag permission.
- **⚠️ Role-assignment authority is hierarchy-aware, and the direction matters — read `isRoleAssignable`'s doc comment before touching it.** A role can assign a role that is *itself or an ancestor of its own `extends` chain* — walking **up** from the actor's own role, never down from the target. This is why HR Manager (`hr-manager -> employee -> intern`) can assign Employee/Intern but **not** Senior Employee/Team Lead/Project Manager/Department Head, even though those might sound "lower" in a casual reading — they're a different branch entirely, not an ancestor of HR Manager's own role. This is a direct, intentional consequence of HR Manager branching off Employee (decided in the role-hierarchy stage, §29) — if that branching ever changes, this consequence changes with it. Company Admin bypasses the whole check (`sourceBlueprintRoleId === "role.admin"`) — the one hardcoded role-id check in the RBAC layer, deliberate and documented, matching the user's explicit "Company Admin can assign any role."
- **`isRowInScope` was deliberately left untouched for `department:manage:own`/`user:manage:own`.** Both are enforced by *explicit, mutation-local* scope checks instead (`ctx.effective.has(...)` compared directly against `ctx.userDepartmentId`), not routed through the generic scope-check dispatcher. Reason: `isRowInScope`'s `"own"` means exactly `ownerId === actor.userId` everywhere else (Project/Task), and `Department`/`User`-placement rows have no ownerId-shaped field for that to mean anything through — extending `isRowInScope` to special-case this would have subtly redefined a well-tested primitive for one resource. **If a future resource needs an "own" scope that isn't a row-ownership check, follow this precedent (bespoke, local, clearly commented) rather than growing `isRowInScope` new branches.**
- **`department.create` requires a literal `"tenant"` scope, not just presence** — `"own"` is rejected outright, not silently narrowed, since creating a brand-new department isn't something "the one I already belong to" can mean. `team.create`/`user.assignDepartment` both constrain the *destination* only (department Head can create a team or place someone into their own department, but the check doesn't also verify a target user's *current* department) — a known, deliberately-flagged simplification, not an oversight; tightening it is a real, separate decision if ever wanted.
- **`users.list` now has real own-scope narrowing** (Department Head sees only their own department's roster) — before this stage `user:manage` only ever existed at `:tenant`, so there was nothing to narrow; don't assume this data source is still unconditionally tenant-wide when reasoning about who can see what.
- **A real modeling fix, not a new feature, found while re-deriving each tier's grants against the user's precise spec**: the original 8-tier hierarchy (§29) had over-broadened `task:update` to `:department` scope at Team Lead. Moved to Project Manager, where a department-wide remit actually belongs; Team Lead now correctly sits at `:team` (already inherited from Senior Employee, no re-grant needed). **If a future permission table edit feels like it's "obviously" the right scope for a tier, sanity-check it against that tier's own precise job description, not just against the tier above/below it** — this is exactly the class of bug that produced the original over-broadening.
- **`task.reassign` is new — the first mutation ever to change a task's `assigneeId` after creation.** Shares a `requireTaskInScope` helper with `task.updateStatus` (same scope-check, extracted rather than duplicated a third time). Both it and `task.create` now reject an `assigneeId` that isn't the project's owner or an existing `ProjectMember` — closes a gap explicitly left soft when `ProjectMember` was built (§27): "assignee must be part of the project" was UI-only before, now enforced server-side too.
- **Delegation (Company Admin granting HR Manager specific extra privileges at runtime) is explicitly out of scope, deliberately** — confirmed via `AskUserQuestion`, not assumed. It needs its own data model (who delegated what to whom, revocation) and deserves the same dedicated-plan treatment role hierarchy itself got. The `user:invite`/`role:assign` split done this stage exists specifically so that stage can slot in cleanly later (grant `user:invite:tenant` to HR Manager's materialized role, or a user-specific override — a small, well-defined addition once designed, not a redesign).
- **Live-verified end-to-end** with a throwaway Company Admin + Department Head + Team Lead + HR Manager + two Employees, covering every rule above including both the presence-gate case (Team Lead, zero `role:assign` grant, `403`s outright) and the hierarchy-walk case (HR Manager, test-granted `role:assign` specifically to exercise the logic, can assign Employee but not Senior Employee). See CHANGELOG for the full run.
- **⚠️ This stage shipped a real bug**, caught by the user's own testing immediately afterward: `isRoleAssignableBy`'s two lookups were originally written as a `Promise.all` against the shared resolver `tx`, which corrupted the transaction and 500'd `user.invite` intermittently. Fixed by making them sequential — see §9's standing rule (never `Promise.all` queries sharing one resolver's `tx`) and the dedicated CHANGELOG bug-fix entry for the full incident, including two more pre-existing instances of the same anti-pattern found and fixed in the same sweep (`projects.data-sources.ts`, `users.data-sources.ts`).

## 36. Org Hierarchy Phase 1 — implementation record (reuse this, don't rebuild it)

`packages/manifest-schema/src/permission.ts` (`SCOPES`), `apps/api/src/rbac/{scope.ts,scope-check.ts,department-subtree.ts}`, `apps/api/src/modules/{tasks,projects,hr,users}/`, `apps/api/prisma/seed.ts`, `apps/api/src/auth/materialize-roles.ts`, `apps/web/src/modules/hr/OrgStructure.tsx`:

- **⚠️ Real bug found live, not caught by unit tests: `materializeDepartmentTypeLabels`'s first implementation did 47 sequential `upsert()` calls** (one per department-type × tier pair in the reference taxonomy) — fine against a plain `PrismaClient` (`seed.ts`'s reseed loop), but **500'd every fresh signup**: `AuthService.signup` wraps its whole body in one interactive transaction with Prisma's 5s default timeout, and 47 sequential round-trips blew past it (`P2028`). Fixed with a single batched multi-row `INSERT ... ON CONFLICT DO UPDATE` (one query, not 47) — not a `Promise.all` (unsafe against a shared `tx`, per the standing rule), a genuinely single statement.
- **⚠️ A second, related real bug found live: `user.invite`'s own transaction also timed out** when Resend's rejection (inviting a non-account-owner email under the sandbox sender) took long enough to push total transaction time past 5s — a **commit**-time failure (`P2028` on commit, not on a query), meaning it happened *after* `user.invite`'s own try/catch had already returned successfully, so its existing rollback-on-failure logic never saw it. This left an orphaned Supabase Auth account (the same failure class as the earlier signup-blocking bug, §33) — found, and cleaned up, live. **Root cause: external HTTP calls (Supabase Admin API, Resend) run inside the same short-lived transaction `TenantPrismaService.run()` wraps every mutation in** — a pre-existing architectural characteristic, not something this stage introduced, just newly triggered by testing a rejection path instead of the success path. **Mitigated by raising `run()`'s transaction timeout to 20s** (`tenant-prisma.service.ts`) — a pragmatic fix, not a structural one. **The real fix (moving external I/O out of the transaction entirely) is a genuine future follow-up** — no mutation resolver today has a way to do "commit, then do X"; flagging this here so it isn't rediscovered as a surprise.

- **`hr.mutations.ts`'s `department.create`/`team.create` don't route through `isRowInScope` at all** (confirmed during exploration — bespoke inline scope checks, a pre-existing pattern this stage extended rather than restructured) — both gained a `"department-subtree"` branch verifying the target department/parent is within the actor's own subtree via `getDepartmentSubtreeIds`.

- **Minimal frontend wiring**: `OrgStructure.tsx` gained a department-`type` `<Select>` on department creation (backed by a new `departmentTypes.list` data source) and a manager picker (`user.setManager`, a new mutation — same `"own"`-scope-constrains-the-target pattern as `user.assignDepartment`). `TeamMembers.tsx` needed zero changes — it already renders whatever `roles.list`/`users.list` return, so the new tier/department-flavored labels just appear, matching the same "reads from the registry, never hardcodes role names" precedent confirmed during the original 2026-07-15 role-hierarchy rollout.

## 39. Performance audit — findings delivered, not yet acted on

A general full-stack performance audit was run (frontend rendering/data-fetching, SDUI rendering pipeline, backend query patterns, DB indexing, Prisma/transaction overhead, Next.js bundle configuration, blueprint-compilation cost) in response to the user's separate ask ("the platform currently feels slow"), tracked independently from the design migration above per the user's own choice to split these into two efforts.

**Ranked findings (highest impact first) — full detail relayed to the user, not reproduced in full here to avoid drift from the actual investigation:**
1. **Per-request transaction pile-up** — a single bootstrap/page request triggers ~7 separate interactive transactions (`resolveIdentity` runs twice, once in `getEtag` and again in `compileWorkspace`/`compilePage`), each its own `BEGIN`/`set_config`/`COMMIT` round-trip.
2. **No client-side caching or ETag reuse** — `apps/web/src/lib/api-client.ts` never sends `If-None-Match` despite full server-side 304 support; every navigation is a fresh, uncached fetch. Compounded by a filter-triggered refetch cascade in `use-data-binding.ts` (changing one `FilterBar` re-triggers every binding on the page, not just ones that reference it).
3. **`compilePage` prunes the entire blueprint for a single-page request** — `permission-pruner.ts` rebuilds every page's node tree even when only one page's content is needed.
4. **Missing indexes** on `Task.assigneeId`, `Project.ownerId`/`departmentId`, `User.departmentId` — exactly the columns the most common scope-filtered queries filter on, confirmed by cross-referencing every `@@index` in `apps/api/prisma/schema/*.prisma` against actual `where` clauses.
5. **Duplicate ad hoc reference-data fetches** across composites (`ProjectBoard`/`TaskList`/`OrgStructure`/`TeamMembers` each independently fetch overlapping `users.list`/`projects.list`/`departments.list`/`teams.list`).
6. **`recharts` is bundled eagerly** (`sdui/primitives/index.ts` statically imports and registers `Chart` for every user, whether or not their blueprint ever renders one) — a `next/dynamic` candidate.
7. Two smaller, fixed-cost (not row-scaling) findings: `projects.list`'s 3 sequential round-trips, and `users.list`'s tenant-wide over-fetch of departments/teams/labels regardless of how many are actually referenced.
8. SDUI renderer/error-boundary overhead was investigated and found **not** to be a real contributor.

**Superseded by §47 (2026-07-20):** this list was static-code-reading guesswork, not measurement — findings #1 and #2 above turned out to be the dominant real cost (confirmed directly), #6 turned out to have negligible real impact (bundle size was never actually large), and findings #3/#5 remain genuinely un-actioned (see §47's "not done this pass" list). Read §47 for what was actually measured, fixed, and re-measured.

**Status: findings only — no fixes applied yet.** This needs its own plan-mode session (the fixes span backend query/index changes, a real caching-layer decision for the frontend, and a call on whether/how to reduce the per-request transaction count without weakening the RLS-via-session-GUC guarantee that currently depends on it) before any code changes, matching this project's standing working agreement.

- **Deletion is hard-blocked at the application layer, not soft-deleted — confirmed necessary, not a stylistic choice.** Direct inspection of the actual migration SQL found `teams.department_id` is DB-protected (`ON DELETE RESTRICT`), but `departments.parent_id` is not (`ON DELETE SET NULL` — silently orphans children) and **`User.departmentId`/`User.teamId` carry zero FK constraint at all.** `department.delete`/`team.delete` both check for children/members first and reject with a specific, human-readable blocker message (`describeDeleteBlockers` — e.g. `"Cannot delete: still has 2 teams, 3 users. Move or reassign them first."`), naming exactly what's blocking rather than a generic conflict error.

Neither auto-demotes an existing head/manager if one already exists — the UI surfaces that as a note, not an automatic side effect.

New per-row Edit/Archive/Delete controls and a "Move to department" select for teams, "Assign head"/"Assign manager" selects for both, a `showArchived` toggle, and a plain `window.confirm(...)` before any delete (no modal component exists anywhere in this codebase — a proportionate choice over building one for this module).
- **⚠️ A genuine, pre-existing production bug found and fixed during this submodule's live browser verification, unrelated to the feature itself: `ERR_HTTP_HEADERS_SENT` on `WorkspaceController`.** Both `bootstrap()` and `page()` used `@Res({ passthrough: true })` and, on a `304` cache-hit, called `res.status(304).end()` followed by a bare `return;`. Nest's own response pipeline then *also* tried to send the (undefined) handler return value afterward, since passthrough mode expects Nest to own the response — throwing `ERR_HTTP_HEADERS_SENT` on any second/repeat request matching the same etag. **React StrictMode's double-effect-invocation in dev makes this the common case, not a rare one** — found live via a hung fetch with zero visible network completion (not by code inspection), and confirmed to affect a second, completely unrelated pre-existing page (`page.team`) via a control test, proving it wasn't specific to this submodule's new code. **Fixed** by switching both methods to full manual `@Res()` control (no `passthrough`) with explicit `res.json(...)` calls on the success path — removing the ambiguity entirely rather than patching around it. **If a future endpoint needs to end the response manually inside a conditional branch (a cache-hit, an early-exit), take full manual `@Res()` control for the whole handler, not just the branch that needs it** — mixing `passthrough: true` with a manual `.end()` on only one path is the exact shape of this bug.
- **Verified end-to-end against the live, fixed API** — not just unit tests: minted a real Supabase session for the test account directly via the Admin API (`generate_link` + `verify`, using the service-role key) rather than needing the account's plaintext password, injected it into a Playwright browser's `localStorage`, then drove repeated navigation across `page.hr` → `page.team` → `page.hr` (deliberately re-triggering the same-etag repeat-request path the bug lived in). Earlier in this same verification pass, delete-blocking, archive round-trip, move-team, and the HR-role-override resolution path were each separately confirmed correct against the live API with real data, then cleaned up — no throwaway data left in the real tenant (`yash-1`).

## 48. Performance pass 2 — architecture-level fixes: real SPA navigation, a real client-side cache, batching (reuse this, don't rebuild it)

`apps/web/src/ui/WorkspaceSidebar.tsx`, `apps/web/src/app/workspace/layout.tsx`, `apps/web/src/lib/query-client-provider.tsx`, `apps/web/src/sdui/use-data-binding.ts`, `apps/web/src/modules/{hr/OrgStructure,projects/ProjectBoard,tasks/TaskList,users/TeamMembers}.tsx`, `apps/web/src/lib/api-client.ts`, `apps/api/src/data-sources/data-sources.controller.ts`, `apps/api/src/config-engine/{compiler.service,permission-pruner}.ts`, `apps/web/src/sdui/primitives/List.tsx`, `apps/web/vitest.config.ts`:

- **⚠️ The headline finding: sidebar navigation was causing a full browser page reload on every click — this app had been behaving like a multi-page site, not a SPA, for its primary navigation path, this whole time.** Proven directly: a `window.__marker` global set after landing on a page vanished after clicking a sidebar link (only a real navigation tears down `window`; a client-side route change never does). Root cause in code: `next/link` was imported **nowhere** in this codebase — `WorkspaceSidebar.tsx`'s nav items rendered plain `<a href>` tags with no `preventDefault`/`router.push`. Every click refetched `bootstrap`/`notifications.unreadCount` from scratch and remounted the entire React tree, on top of whatever the target page's own data cost — measured at **~5.8-5.9s for `page.hr`, ~2.2-2.4s for `page.team`, on every single click, including "repeat" visits to a page seen seconds earlier**, against a **production build** (so not a React StrictMode dev-mode artifact). Confirmed via the same marker test: `before === after` now holds.
- **Two context providers were passing a brand-new object literal as `value` on every render** (`RenderContextProvider`/`BootstrapContextProvider` in `layout.tsx`) — every consumer of `useRenderContext()`/`useBootstrap()` across the whole rendered tree re-rendered on any layout state change (sidebar collapse, command palette open/close), even though the underlying values never changed. **Fixed** with `useMemo`/`useCallback`, placed *before* the component's early returns per the Rules of Hooks (`commandItems`'s existing `useMemo` already established this precedent in the same file).
- **Adopted TanStack Query (`@tanstack/react-query`) as the client-side data-fetching/cache layer underneath `useDataBinding` — the real architectural decision this pass made, not a micro-fix.** Before this, only page *structure* was cached (pass 1's manifest ETag cache); the actual data underneath (`departments.list`, `users.list`, `tasks.list`, …) had zero caching, zero cross-component dedup, and zero stale-while-revalidate — revisiting a page one second later refetched everything from a blank slate. **Chosen over hand-rolling a second cache**: `useDataBinding`'s external contract (`{data, loading, error, refetch}`, now also `queryKey`) didn't change, so every primitive calling it needed zero changes — only the hook's ~50 internal lines changed, plus one `QueryClientProvider` near the root. Request dedup, stale-while-revalidate, and a real prefetch API come for free and correctly, rather than being re-solved by hand (race conditions on rapid navigation, in particular, are exactly the kind of thing a hand-rolled cache gets subtly wrong). `loading` maps to TanStack's `isPending` (true only before any data has ever arrived), not `isFetching` — a background refresh no longer flickers a loading state, which is the actual mechanism that makes revisits feel instant.
- **The cache benefit was extended to composites, not just simple blueprint-bound primitives — a real, necessary extension found during this pass, not originally planned.** `OrgStructure` bypassed `useDataBinding` entirely (4 hand-rolled `useEffect`+`useState`+`callDataSource()` fetches); `ProjectBoard`/`TaskList`/`TeamMembers` each had *secondary* ad hoc fetches (a member/project/role/department picker's roster) alongside their primary `bind`-based one. All of these bypassed the new cache until migrated onto a new shared `useDataSourceQuery(source, params)` hook (same query-key scheme as `useDataBinding`, so a composite and a blueprint-bound primitive asking for the same `source`+`params` now share one cache entry) — this is also what finally closes the original static audit's long-flagged, never-fixed "duplicate ad hoc reference-data fetches across composites" finding (§39's #5).

A per-item failure returns `{ error }` for that item only, not a whole-batch rejection. New client `useDataSourceBatchQuery(requests)` hook calls it and also seeds each result into the individual per-source cache entry (`queryClient.setQueryData`) so anything else on the page asking for the same source+params separately still gets an instant hit. `OrgStructure` (the worst offender — 4 sources) is migrated onto it; measured **~2.6s for all 4 sources together, down from summing 4 separate calls (~7-8s)** — bounded much closer to the cost of the single heaviest source than to their sum, since the transaction-wrapper tax is now paid once instead of 4 times.
- **Hover-intent prefetch** (`WorkspaceSidebar`'s `onMouseEnter` → `layout.tsx`'s `prefetchPage`): fetches the target page's tree ahead of a click and walks it (`collectSourceBindings`) to `queryClient.prefetchQuery` every *blueprint-bound* primitive's data too. **Disclosed limitation, not a bug**: a composite's own internal reference-data needs (e.g. `OrgStructure`'s `departments.list`/etc.) aren't expressed as a `bind` on any node, so they can't be discovered statically without executing the component — prefetch covers primitives directly, not composites' secondary fetches.

## 50. Core Workspace Modules, Phase 1 — Communication & Collaboration: Channels & Direct Messages (reuse this, don't rebuild it — especially the Realtime findings)

`apps/api/prisma/schema/chat.prisma`, `apps/api/src/modules/chat/{chat.mutations,chat.data-sources,chat.module}.ts`, `apps/api/src/rbac/`-adjacent migrations (`fix_missing_rls_policies`, `chat_conversations_messages`, `fix_realtime_membership_recursion`, `grant_realtime_select`), `apps/web/src/sdui/use-realtime.ts`, `apps/web/src/modules/chat/ChatWorkspace.tsx`:

- **Second submodule of the Core Workspace Modules roadmap.** Unlike Comments & Mentions, this one needed genuinely new infrastructure — real-time transport — the first use of Supabase Realtime anywhere in this codebase, and it surfaced a real, multi-layered set of findings worth reading in full before touching Realtime again.
- **One unified `Conversation` model for both Channels and DMs** (`type: "channel" | "dm"`) rather than two parallel schemas — a DM is just a private, unnamed, 2-member conversation, matching Slack/Discord's own internal shape. `ConversationMember` (membership + `lastReadAt` for unread counts) and `Message` (soft-deleted, matching Comment/Project/Task) round out the schema. `conversation.createDm` is idempotent — looks up an existing 2-member `"dm"` conversation before creating a new one.
- **No new permission triples — membership is the scope**, same idiom as Comments: `assertConversationMember` mirrors `assertCommentTargetInScope`'s existence-then-scope shape. `conversation.addMember` deliberately handles two distinct cases in one mutation rather than a separate `conversation.join`: adding *someone else* requires existing membership (private-channel invite semantics); adding *yourself* is a self-join, allowed only when the channel isn't private — this is what makes `channels.list` (browsable public channels) actually usable. `conversation.archive`/`message.delete` are creator/author-only, mirroring `comment.delete`.
- **⚠️ Decision made and disclosed, not silently assumed: private channels are not visible to Company Admins who aren't members** — same strict "private means private" model as Slack/Teams. Revisit only if a future Audit/Compliance submodule explicitly asks for admin oversight into private content.
- **⚠️ Real bug, caught by two truly concurrent requests during this submodule's own verification: a check-then-create race in `conversation.addMember`'s self-join path.** A double-click self-join hit a raw 500 (`P2002` unique-constraint violation) — worse, **Prisma 7's own `upsert` also threw the same raw error under genuine concurrency** rather than compiling to an atomic single statement, and neither a caught exception nor `upsert` could be recovered from with a followup query on the *same* transaction (Postgres aborts the whole transaction the instant one statement in it errors — `25P02`, "current transaction is aborted"). **Fixed with raw `INSERT ... ON CONFLICT DO NOTHING RETURNING *`** (`tx.$queryRaw`, same precedent as `getDepartmentSubtreeIds`'s raw CTE) — the one path that's genuinely atomic and never errors on conflict, so a fallback `findFirst` on empty `RETURNING` is safe. Verified with 5 truly concurrent requests resolving to the identical row.
- **⚠️ The real architectural wrinkle, exactly as flagged in the approved plan: Realtime needs a second, JWT-based RLS policy** alongside every existing GUC-based `tenant_isolation` policy, since the browser's own Realtime connection never sets `app.tenant_id`. Uses the `tenant_id` claim the `custom_access_token_hook` already stamps on every JWT (Stage 2), plus membership, via a new `realtime_membership` policy on all three chat tables.
- **⚠️ A second, non-obvious RLS bug this same policy introduced: infinite recursion.** `conversation_members`' own `realtime_membership` policy queried `conversation_members` from inside its own `USING` clause's `EXISTS` — Postgres detects this as recursive the instant anything touches the table (`42P17`). **Fixed with the standard Postgres/Supabase pattern**: a `SECURITY DEFINER` helper function (`is_conversation_member(conversation_id, auth_uid)`, same technique as `custom_access_token_hook`) whose internal query bypasses RLS, breaking the recursion. `conversations`/`messages`' policies (querying `conversation_members` from a *different* table) were never affected — only a table's policy referencing itself is recursive.
- **⚠️ A third, genuinely surprising infrastructure finding: every table in this project had only ever been `GRANT`ed to the custom `app_runtime` role, never to Supabase's built-in `authenticated` role** — RLS controls row visibility, but Postgres also requires table/column-level privilege before a role can query at all, and Realtime evaluates a subscriber's `postgres_changes` filter *as* `authenticated` (mirroring how PostgREST does it). With zero privileges there, subscribing failed with a deeply misleading error: `ERROR P0001 (raise_exception) invalid column for filter conversation_id` — which reads like a schema problem, not a permissions one. **Fixed**: `GRANT SELECT ON conversations, conversation_members, messages TO authenticated;`. No prior table ever needed this, since nothing before this submodule ever used Realtime.
- **⚠️⚠️ The most significant finding of this submodule, disclosed rather than worked around silently: after fixing all three issues above, `INSERT` `postgres_changes` events are still never delivered by this Supabase project's Realtime service — confirmed by exhaustive, methodical elimination, not assumed.** Verified via a bare Node `@supabase/supabase-js` client (no React/browser involved): a fresh, valid JWT; RLS temporarily set to `USING (true)` (fully open — ruled out policy logic entirely); `REPLICA IDENTITY FULL` tested (no change); publication membership, grants, `wal_level = logical`, and replication-slot health (`pg_stat_replication`, <100ms lag) all confirmed correct; a 100+ second wait (ruled out slow service-side cache propagation). **`DELETE` events on the same tables, same subscription mechanics, deliver correctly** — proving the pipeline works end-to-end for at least one event type, which rules out the websocket/topic/auth layer wholesale and narrows this to something INSERT-specific inside the managed Realtime service itself. This is an external, disclosed limitation of this environment — not an app bug, and not something fixable from application code or SQL migrations alone (no Supabase Dashboard/support access available from here).
- **Fix: `messages.list` polls (`refetchInterval: 4000`) while a conversation is open — this is the actual delivery guarantee, not the Realtime subscription.** `useRealtimeMessages` stays wired up as a best-effort accelerator (instant delivery for free if the INSERT-delivery limitation above is ever resolved) but is explicitly documented as non-load-bearing. Verified live: with polling in place, a message sent in one real browser session appears in a second real session within the poll interval, both directions, with zero manual refresh.
- **A related, pre-existing RLS gap found while reading every migration for this plan, fixed as a bundled prerequisite**: `comments`, `comment_mentions`, and `department_type_role_labels` (Company Administration, Submodule C onward) were never given the standard `tenant_isolation` policy — a silent drift from ARCHITECTURE.md §8.2's stated invariant, closed in `fix_missing_rls_policies` before three more new tables joined them. No live vulnerability (app-layer scoping already covered every query), but worth having caught before it compounded further.
- **New `nav.chat`/`page.chat`** — no placeholder existed before this (unlike `nav.meetings`'s "coming soon" stub) — visible to every tenant member, no `requiredPermission`, same treatment as `nav.dashboard`/`nav.settings`. `ChatWorkspace` is a blueprint-registered composite (unlike `CommentThread`) — a whole two-pane chat UI is a real top-level page, not a per-row expansion.
- **First real cursor pagination in this codebase** — `messages.list`'s `before` param. The manifest schema's `paginate: boolean` field has never been implemented anywhere; this is new, not a reuse.
- **20 new backend tests**, full backend suite **166/166 passing**, full monorepo typecheck clean, frontend suite **7/7 passing** (unchanged — verified live instead, same precedent as Comments & Mentions).
- **Verified end-to-end against the live, real app**: direct API calls (channel create/join/browse, private-channel 403s on both read and self-join, DM idempotency confirmed identical on a second call, mention notifications, unread-count drop on `markRead`, ownership-gated message delete) plus a full two-real-browser-session Playwright walkthrough proving actual cross-session message delivery (via the poll, given the disclosed Realtime limitation above) in both directions. Every test conversation/message/membership row deleted outright (not just archived) from the real tenant (`yash-1`) afterward — this submodule's verification, being schema/infrastructure-focused, generated an unusually large number of throwaway channels across many debugging iterations, all confirmed removed (`SELECT count(*)` on all three tables returned 0 before finishing).
- Confirmed `ORG_HIERARCHY.md` needs no change — no authority-model impact.

Retrieval degrades silently to "no context" (never a hard failure) if the embedding provider isn't configured — Phase A's core promise (basic chat) must keep working even if embeddings are independently misconfigured. Retrieved chunks are folded into the system prompt fresh every turn and **never persisted as a stored message**, so stale retrieved content can't leak into a later turn's replayed history.
- **Document text extraction deliberately scoped to only `text/plain`, `text/csv`, and `application/pdf`** — Documents' own upload allowlist is broader (docx/xlsx/pptx/zip/images); everything else gets no `EmbeddingJob` at all this phase, a deliberate scope cut (each has its own natural future extraction library), not a silent drop. **PDF extraction uses `unpdf`, not the more commonly-known `pdf-parse`** — confirmed live: `pdf-parse`'s current major ships `@napi-rs/canvas` as a hard native dependency for no benefit here; `unpdf` has zero required native deps, is actively maintained, and its real API (`getDocumentProxy` → `extractText`) matches exactly what was assumed before installing it.
